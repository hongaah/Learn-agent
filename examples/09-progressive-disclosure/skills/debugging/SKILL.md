# 系统化调试

调试最贵的不是修复本身，是走错方向后再走回来。多数时间浪费在「凭一次读代码的直觉」直接改一处，改完发现没用，再猜下一处——猜的成本比按顺序定位高得多。这份指南按四个动作排序：先复现，再二分，再读栈，最后改一处验一处。

## 先复现，再猜

在看一行代码之前，先把问题稳定复现出来。复现不了的 bug 没法验证「修好了没有」——改完看起来正常，很可能只是这次运气好没触发。

- 记下触发条件：输入是什么、环境是什么、复现率是 100% 还是偶发。偶发的 bug 大概率是并发或者时序问题，复现步骤要包含「重复跑 N 次」而不是跑一次看运气。
- 找到最小复现路径。生产环境的报错往往夹杂大量无关上下文，先把无关变量砍掉，砍到「改动这一个条件，问题就消失」为止。
- 复现不出来就先别下结论。「应该是这里」这种判断在没有复现实验支撑之前只是猜测，猜测直接写进代码就是在给下一个 bug 铺路。

## 二分定位

问题范围大（不知道是哪个模块、哪次提交、哪个函数）的时候，靠读代码猜是线性搜索，靠二分是对数搜索——二十次线性尝试，二分七八次就够。

- **对提交历史**：用 `git bisect`，标记「好」和「坏」两个版本，让工具在中间跑，自动收敛到第一个引入问题的提交：

  ```
  git bisect start
  git bisect bad HEAD          # 当前版本有问题
  git bisect good v1.2.0       # 这个版本还是好的
  # 每次 checkout 到中间版本后跑一遍复现步骤，再告诉 bisect 结果
  git bisect good   # 或 git bisect bad
  ```

- **对调用链**：在链路中点插一个探针（打印、断点、临时返回值），看问题出现在探针之前还是之后，把范围砍半，重复。
- **对数据**：怀疑是某条输入触发的，用二分法从全量数据里砍出最小的触发子集，而不是逐条排查。

二分的前提是每一步都有一个明确的「是/否」判断——先想清楚这一步怎么判断「问题出现在前半段还是后半段」，想不清楚就先设计一个能回答这个问题的探针，再动手砍范围。

「最近改动过的地方优先怀疑」是二分思路的特例：如果问题是今天才出现的，且今天只有一次部署，根因大概率就在这次部署的 diff 里，不需要从整个代码库开始排查，直接对着这次 diff 走一遍前面几条规则就够了。

## 读完整栈

报错信息和堆栈是免费的线索，大多数人只看第一行就开始猜，浪费了后面更有价值的部分。

- **从异常类型和消息开始**，但不要止步于此——同一个 `TypeError` 在十个地方都可能抛，光看类型定位不到具体位置。
- **顺着调用栈往下找到自己写的代码那一帧。** 框架内部的栈帧通常不是根因所在，你的代码调用框架的那一行、传了什么参数，才是该看的地方。
- **注意「caused by」「inner exception」这类嵌套错误。** 外层异常经常是包装过的，真正的根因在内层，只看外层容易修错地方。
- **警告也是信号。** 不是只有报错才算线索，运行时警告、类型检查器的提示，经常提前指出了后面才会炸的问题。
- **对比「期望的值」和「实际的值」，不要只看「报错了」这个事实本身。** 打印或断点看关键变量在出错前一刻的真实内容，很多时候差异一眼就能看出根因，比读源码猜测快得多。

## 改一处验一处

定位到疑似根因后，一次只改一个变量，改完立刻用最初的复现步骤验证，再决定下一步。

- **不要一次改多处。** 同时改三个地方问题消失了，不知道是哪一个起作用的——下次遇到类似问题，判断力没有增长，靠的还是运气。
- **每次修改都要能回答「为什么这个改动能解决刚才定位到的根因」**，回答不出来说明还没真正定位，只是在试概率。
- **验证用的是最初能稳定复现问题的那条路径，不是「看起来正常了」。** 偶发问题尤其要重复跑多次，一次不报错不能证明修好了。
- **修完之后回头看一眼影响范围。** 这处改动会不会影响其他调用方？是不是应该补一个回归测试，防止同样的根因下次换个触发路径又出现。

## 常见反例

- **没复现就直接改。** 看了一眼报错就「猜测应该是这里」，改完自己都不知道有没有解决，只是把问题换了个位置。
- **一次改一大片。** 「反正顺手也重构了一下」——出了问题分不清是重构引入的还是修复本身的效果。
- **只看错误的第一行就下结论。** 忽略了嵌套异常里真正的根因，修的是表面症状。
- **线性扫描代码库找问题。** 明明有二分的条件（能确定好坏两个版本、能在链路中插探针）却不用，纯靠通读代码找茬。
- **修好一处不验证就继续改下一处。** 几个小时后发现最初那处其实没解决，前面的调试全部要推倒重来。

## 检查清单

1. 能稳定复现吗？不能就先把复现步骤做稳，再往下走。
2. 范围能二分吗？能就别线性排查，"最近改动过的地方"是最值得优先二分的一半。
3. 堆栈从头到尾读完了吗，还是只看了第一行？期望值和实际值对比过了吗？
4. 这次只改了一处吗？改完用最初的复现步骤验证了吗？
5. 能不能把这次的根因写成一句话？写不出来说明还没真正定位，只是运气好问题不再出现。
