# 写好一条提交信息

好的提交信息回答一个问题：六个月后，看不到代码本身的人，为什么要做这次改动？diff 已经如实记录了改了什么；提交信息不重复这件事，它补的是 diff 里看不出来的东西——动机、权衡、排除掉的方案。

## 主题句

- 一行，动宾结构，祈使语气：「修复」「新增」「重构」，不是「修复了」「新增了」。
- 中文项目控制在 25 个字以内，英文项目控制在 50 个字符以内。超过说明这一条提交做了不止一件事，应该拆成两条。
- 前缀固定几种，别自造：`feat`（新功能）、`fix`（修 bug）、`docs`（文档）、`refactor`（不改行为的重构）、`test`（测试）、`chore`（杂项，构建脚本、依赖升级）、`perf`（性能）。
- 主题句不加句号，不要「更新代码」「修改若干文件」这类不携带信息的动词加泛指宾语——宾语必须具体到「改了什么模块、什么行为」。

## 什么时候要正文

不是每条提交都要正文。主题句已经把「改了什么」说清楚、且改动本身显而易见时，正文是噪音，不用写。

需要正文的情况：

- **动机不在代码里。** 比如为什么选了这个算法而不是更直觉的那个，为什么绕开了某个 API。
- **有阵痛但必须做。** 破坏性变更、临时 workaround、已知有局限的权衡——不写清楚，下一个改这块代码的人会以为是失误，顺手「修复」掉。
- **修 bug 但触发条件不直观。** 说清楚复现路径和根因，而不是只说「修了个 bug」。
- **这条提交同时动了好几个看起来不相关的文件。** 正文解释为什么它们其实是同一件事。

主题句和正文之间空一行；正文用列表或短段落，不要写成小作文。

## 写「为什么」不写「改了什么」

diff 本身就是「改了什么」的最权威记录，提交信息重复它是浪费读者的时间。该写的是 diff 里看不出来的决策过程。

反例：

```
修改 retry.ts

把重试次数从 3 改成 5，把 sleep 时间从 1s 改成 2s。
```

这两句话打开 diff 就能看到，正文等于白写。

正例：

```
fix: 提高重试次数与退避时间，应对第三方接口高峰限流

高峰期第三方接口 429 概率上升到 15%，3 次重试在最坏情况下
仍有约 3% 请求彻底失败。改成 5 次加指数退避后，压测环境
失败率降到 0.1% 以下。
```

同样是改两个数字，第二版讲清楚了「为什么是这两个数字」，第一版只是把 diff 抄了一遍。

## 常见反例

- **「fix bug」「update」「WIP」。** 没有任何可搜索、可追溯的信息，六个月后 `git log --grep` 根本查不到这条提交在改什么。
- **一条提交塞两件不相关的事。** 「修复登录 bug，顺便升级了几个依赖」——以后 revert 登录修复时会把依赖升级也一并带走。
- **主题句写成过程叙述而不是结果。** 「尝试修复内存泄漏」——不确定就不要提交到主线，提交历史不是草稿纸。
- **正文复述主题句。** 主题句已经说了「修复空指针」，正文又写一遍「本次提交修复了空指针问题」，没有增量信息。
- **只写技术动作，不写触发场景。** 「加了个 null 检查」——检查了哪个字段、什么条件下会是 null、不检查会造成什么后果都没交代，review 时没法判断这个检查加得对不对。

## 检查清单

1. 这条提交只做一件事吗？如果要用「和」字才能描述清楚，考虑拆分成两条。
2. 主题句离开代码上下文，单独读一遍，还能看懂在做什么吗？
3. 如果正文只是在复述「改了什么」，删掉它——diff 已经说了。只有正文能回答「为什么」时才留着。
