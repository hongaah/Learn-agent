# 代码审查看什么、怎么说

代码审查的目标不是「挑出问题证明自己看过」，是让改动能安全地合到主线，且不给作者制造无谓的返工。这决定了两件事：看的顺序，和说的方式。

## 正确性优先于风格

按下面的顺序看，前面的问题不解决，后面的不值得花时间：

1. **正确性。** 这段代码在正常输入下、边界输入下、并发场景下，是不是真的做了它应该做的事。
2. **安全性。** 有没有引入注入、越权、密钥泄露、反序列化风险。
3. **健壮性。** 错误处理是不是完整，失败路径会不会让系统处于不一致状态。
4. **设计。** 这个改动放在这个位置合不合适，有没有引入不必要的耦合。
5. **性能。** 只在这条路径确实是热点时才值得纠结。
6. **风格。** 命名、格式、注释密度。

一个只有风格问题、没有上面 1-5 问题的 PR，应该被批准，风格意见留作 nit（见下）不阻塞合并。反过来，一个格式完美但有并发 bug 的 PR，不该因为「看起来很干净」就被放过。

先看风格再看逻辑是最常见的审查反模式——花二十分钟对齐了缩进和命名，最后才发现这个函数在并发下会死锁，前面的时间全部浪费。

## 怎么提可执行的意见

好评论具体到哪一行、什么问题、怎么改，读的人不用再问一轮就能动手。

反例：「这里感觉不太好」「可以优化一下」——不知道哪里不好、往哪个方向优化，作者只能靠猜，往返成本比不评论还高。

正例的结构：

```
第 42 行：这里在循环里对 users 做线性查找，n 大的时候是 O(n²)。
建议改成先建一个 Map<id, User>，查找降到 O(1)。
```

三个要素缺一不可：指出具体位置、说明问题的后果（不是「不优雅」而是「O(n²)」）、给出可执行的方向。

意见不确定的时候用问句而不是断言：「这里没加锁，是确认过调用方都在同一个线程里吗？」——比「这里应该加锁」更诚实，也给作者解释语境的机会，语境如果站得住，评论就该撤回，而不是坚持己见。

## 什么该评论、什么该直接改

区分三类问题，处理方式不一样：

- **阻塞性问题**（bug、安全漏洞、破坏现有行为）——必须评论并要求作者修改，不能自己代劳改掉再合并，作者需要理解为什么错，以后才不会重复犯。
- **可选建议**（更好的命名、可以但非必须的重构）——标 `nit:` 前缀留言，明确「不采纳也能合并」，别让这类意见拖住整个 PR。
- **纯格式问题**（缩进、空格、自动化工具能修的东西）——不值得占用 review 来回，能自己顺手改的直接改，改不了就配 lint 或 formatter 自动跑，不要用人工评论解决机器该解决的问题。

判断标准：这条意见不采纳，代码会出错或者显著变差吗？会——阻塞；不会——nit 或者干脆不提。

给评论加前缀，让作者一眼分清轻重，不用逐条判断你的语气是认真的还是随口一提：

- `blocking:` 不改不能合并。
- `question:` 只是确认理解，作者答对了就翻篇，不代表需要改代码。
- `nit:` 可选的小建议，作者可以直接忽略。

## 别忘了说好的地方

审查不是只找茬。看到一个巧妙的解法、一次好的边界处理，顺手说一句——这不是客套，是在告诉作者「这个模式是对的，继续这样写」，跟指出问题同样是在校准对方的判断力。只挑毛病的审查容易让作者只学会「怎么不被挑刺」，而不是「怎么写得更好」。

## 常见反例

- **只挑格式，不看逻辑。** 通篇评论分号和空行，放过了一个明显的空指针。
- **意见模糊不落地。** 「这个函数太长了」——长多少算长？拆成几个？拆分点在哪？不给方向的意见等于没提。
- **把个人偏好包装成必须项。** 「我更喜欢用 for 而不是 map」不是缺陷，标 nit 或者不说。
- **审查变成重新设计。** 在评论区提出和原方案完全不同的架构，应该私下讨论或者补一份设计文档，不要在 PR 评论里临时推翻方案。
- **只说「不行」不说「为什么」和「怎么办」。** 让作者知道错在哪、错的后果是什么、往哪个方向改，三者缺一，返工就要多走一轮不必要的追问。

## 检查清单

1. 先过一遍正确性和安全性，再看设计和风格。
2. 每条评论能不能让作者不追问就动手改？不能就把「哪里、为什么、怎么改」补全。
3. 这条意见不改会出错吗？会才阻塞，不会就标 nit 或者自己顺手改掉。
4. 有没有至少说一句做得好的地方？全篇都是问题，通常说明看漏了对的部分。
